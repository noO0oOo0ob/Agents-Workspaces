# AgentBoard 后续迭代规划

> 前置条件：P0 已完成 Codex + Claude Code 的本机完整闭环
> 本文只规划后续方向，不展开 P0 级技术细节

## 1. 路线原则

后续迭代遵循以下顺序：

1. 先提高本机闭环的可靠性，再扩展远程执行；
2. 先支持个人稳定使用，再考虑团队协作；
3. 继续只深度支持 Codex 和 Claude Code，暂不追求 Agent 数量；
4. 控制平面和执行平面保持解耦；
5. 凭证、知识库和代码默认由用户掌控；
6. 自动化外部副作用必须保留明确审批边界。

## 2. 版本路线概览

```mermaid
flowchart LR
    P0["P0 本机完整闭环"] --> P1["P1 稳定性与远程 Runner"]
    P1 --> P2["P2 Git 托管与知识同步"]
    P2 --> P3["P3 多设备与团队协作"]
    P3 --> P4["P4 智能调度与平台化"]
```

## 3. P1：稳定性与远程 Runner

### 3.1 目标

让 AgentBoard 可以稳定地运行长任务，并允许把执行环境从本机 Docker 扩展到用户自己的远程服务器。

### 3.2 计划能力

- 独立 Runner 进程；
- 通过 SSH 安装或注册 Runner；
- 远程 Docker Execution Profile；
- Runner 心跳、版本和容量状态；
- 远程 Workspace 创建和清理；
- 日志、事件和审批通过加密通道回传；
- Gateway 或 Runner 重启后的会话恢复；
- Interaction 超时、失效和补偿机制；
- Session 崩溃检测和一键续跑；
- Docker 镜像模板和预热；
- 项目级 CPU、内存、磁盘限制；
- 更完整的本地事件审计。

### 3.3 凭证方向

- 本机 Docker 继续使用 Provider 专用持久卷；
- 远程 Runner 默认要求在远端单独完成一次登录；
- 不直接同步整份本机用户目录；
- 如果未来支持凭证迁移，必须采用显式导出、端到端加密、有效期和撤销机制；
- Gateway 只保存凭证 Profile 的元信息，不保存可直接使用的明文 Token。

### 3.4 不在 P1 中完成

- 公有云托管控制面；
- 多用户组织；
- 自动跨云调度；
- 按量计费系统。

## 4. P2：Git 托管与知识同步

### 4.1 Git 工作流

- GitHub/GitLab Repository 元数据同步；
- 从 Issue 创建 Task；
- 自动创建 Draft PR；
- 多仓库 PR 关联；
- PR Check、CI 状态回传；
- Review Comment 转换成继续修改任务；
- 合并前策略检查；
- 推送、创建 PR 和合并继续要求用户审批。

### 4.2 Obsidian 备份与同步

支持可选方案，不强制用户迁移知识库：

1. Obsidian 官方 Sync；
2. 私有 Git 仓库；
3. NAS 文件同步；
4. 用户自建对象存储或同步服务。

AgentBoard 只负责：

- 检查 Vault 是否存在未同步修改；
- 展示知识版本；
- 在编译上下文时记录来源 commit/hash；
- 冲突时停止自动覆盖；
- 对敏感目录提供排除规则。

### 4.3 Memory 演进

- 从“知识候选 Inbox”升级为可审阅的 Memory 提案；
- 展示提案来源 Task、Session 和证据；
- 支持接受、编辑、拒绝和过期；
- 区分全局、项目、仓库和临时 Memory；
- 检测相互冲突或过期的规则；
- 不直接同步 Provider 内部的不可解释 Memory；
- Obsidian Markdown 继续作为权威来源。

## 5. P3：多设备与团队协作

### 5.1 控制面

- 可选的自托管 Server；
- 多设备登录；
- HTTPS 和设备授权；
- 项目成员与 RBAC；
- Task 分配和关注；
- 审批人配置；
- 完整审计日志；
- 浏览器和移动端通知。

### 5.2 审批协作

- 指定审批人；
- 高风险操作双人审批；
- 审批委托；
- 过期和升级策略；
- Review Checklist；
- 团队级安全规则和只读策略。

### 5.3 知识协作

- 知识提案 Review；
- 文档所有者；
- 敏感知识访问控制；
- 项目规则版本发布；
- Agent 运行时上下文可追溯。

## 6. P4：智能调度与平台化

### 6.1 Agent 编排

- 根据任务类型推荐 Codex 或 Claude Code；
- 将大任务拆成子任务；
- 仓库和文件级编辑锁或冲突预警；
- 多 Agent 依赖图；
- 失败自动重试和替代策略；
- 专用 Review Agent；
- 并行度、资源和优先级调度。

### 6.2 质量与成本

- 按 Task/Session 统计运行时间和用量；
- 统计审批等待时间；
- 统计一次通过率、返工率和 CI 成功率；
- 任务模板和基准测试；
- Provider 能力差异报告；
- 长期可靠性和性能趋势。

### 6.3 平台扩展边界

只有当 Codex 与 Claude Code 的适配层、状态语义和恢复能力长期稳定后，才评估第三种 Agent。新增 Provider 必须满足：

- 可结构化启动和终止；
- 可捕获生命周期事件；
- 可完成审批双向回传；
- 可完成用户问题或表单双向回传；
- 可保存并恢复会话身份；
- 不依赖不稳定的终端文字匹配作为主要方案。

## 7. 优先级池

### 高优先级

- 会话恢复可靠性；
- 远程 Docker Runner；
- Interaction 断线恢复；
- GitHub/GitLab PR 闭环；
- Obsidian 可追溯同步；
- macOS 之外的控制台访问。

### 中优先级

- 多 Agent 子任务依赖；
- 自动 Review；
- 项目模板；
- 资源配额；
- 统计报表；
- 团队审批。

### 低优先级

- Electron/Tauri 桌面壳；
- 移动端原生 App；
- 插件市场；
- 第三种 Agent；
- 公有云 SaaS；
- 自动计费。

## 8. 关键决策检查点

进入每个阶段前需要重新确认：

| 检查点 | 需要回答的问题 |
|---|---|
| P0 → P1 | 本机双向交互是否足够稳定，能否恢复异常会话？ |
| P1 → P2 | 远程执行的凭证和网络模型是否安全、可解释？ |
| P2 → P3 | 单用户数据模型是否能够平滑升级到多用户？ |
| P3 → P4 | 调度带来的复杂度是否真正提高交付效率？ |

后续版本不应破坏 P0 的核心特性：即使没有云服务器、Git 平台集成和同步服务，用户仍然可以在一台 Mac 上完整使用 AgentBoard。
