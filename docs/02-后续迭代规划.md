# Agents-Workspaces 后续迭代规划

## 原则

- 先保证本机闭环可靠，再增加远程能力；
- 先服务单用户，再设计团队协作；
- 继续深度支持 Codex 和 Claude Code，不以 Agent 数量为目标；
- 控制平面和执行平面保持解耦；
- 代码、凭证和知识默认由用户掌控。

## P1：稳定性与远程 Runner

- 独立 Runner 进程；
- SSH 注册远程 Runner；
- 远程 Docker Workspace；
- Runner 心跳、容量和版本；
- 日志与审批加密回传；
- Interaction 断线恢复；
- Agent Session 崩溃续跑；
- 镜像模板、预热和资源限制；
- 远端独立登录和凭证 Profile。

## P2：Git 托管和知识同步

- GitHub/GitLab Issue 创建任务；
- 自动创建 Draft PR；
- 多仓库 PR 关联；
- CI 与 Review Comment 回传；
- Obsidian 官方 Sync、私有 Git 或 NAS 可选同步；
- Knowledge Manifest 记录同步版本；
- Memory 提案接受、编辑、拒绝和过期；
- 检测规则冲突和过期知识。

## P3：多设备与团队

- 自托管 Server；
- HTTPS 和设备授权；
- 项目成员与 RBAC；
- 指定审批人和双人审批；
- 审批委托、超时和升级；
- 团队 Review Checklist；
- 浏览器和移动端通知；
- 知识提案 Review 与文档所有者。

## P4：智能编排

- 根据任务类型推荐 Codex 或 Claude Code；
- 大任务拆分和依赖图；
- 仓库/文件冲突预警；
- 专用 Review Agent；
- 失败重试和替代策略；
- 资源和优先级调度；
- 运行时间、等待时间、返工率和 CI 成功率统计。

## 新增 Provider 的门槛

未来只有满足以下条件才考虑第三种 Agent：

- 可结构化启动、停止和恢复；
- 可捕获生命周期事件；
- 可双向处理权限审批；
- 可双向处理用户问题；
- 不以终端文案匹配作为主要控制方案。
